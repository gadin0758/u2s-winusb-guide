# 实测记录：F50 B15 → B09，保留原基带和 NV

这是一个设备的结果，不是所有 F50 或所有中兴设备的兼容性保证。仅发布过程和统计，不公开原镜像、后台密码、设备身份和原始日志。

## 起点与通信问题

**公开版对应脚本：** [Start-Fdl2.ps1](../scripts/Start-Fdl2.ps1) 建立下载连接，正常连接时调用 [f50.py](../scripts/f50.py)；Python 配套文件是 [f50lib.py](../scripts/f50lib.py)。本页记录现场原型的结果，公开版是后来整理的版本。

原系统 B15，用户不愿短接，ADB 未可用。SPRD U2S Diag 能显示 COM 口，原 signed sprdvcom 4.20.42.134 绑定正确，但通信发生串口写入错误（现场 Windows 写入超时 121）。关闭占用程序、改变线/接口后仍出现问题，不能简单归因于漏装驱动。

对 `1782:4D00` 下载设备改绑 WinUSB，使用 LibUSB 后端；分开 mode 2 请求与重新枚举交接，成功加载 FDL2。修改过的原驱动注册表设置已经恢复，教程不依赖那些改动。

## 先完成备份

**公开版对应脚本：** [f50.py](../scripts/f50.py) 的 `backup` 保存备份，`verify-backup` 检查备份；需配套 [f50lib.py](../scripts/f50lib.py)。

先把能读取的系统、启动文件、两套基带和联网设置、用户数据都备份到电脑上。这次共保存了 76 个镜像文件，约 31 GB，并另外保存了分区表。全部文件检查通过后，才开始刷写。具体怎么备份、怎么看是否成功，见 [备份教程](backup.md)。

完整备份保存在本地，开源版本不会包含其文件或个人路径。

## B15 Root 尝试与恢复

曾尝试刷入修改过的启动文件，但没有确认 Root 成功，ADB 也没有确认能用。后来把原来的启动文件恢复并检查，USB 网络和移动网络恢复正常。**文件刷进去，不等于 Root 成功；USB 网络暂时消失，也不能直接认定设备已经刷坏。**

## 系统包自己找，留意这些失败原因

**请自行寻找适合自己设备的系统包。** 本教程不提供或推荐具体包体，也不能因为这次刷成功了，就保证你找到的包也能用。

常见的失败原因有这些：

| 可能的问题 | 怎么看、怎么办 |
| --- | --- |
| 包不是给你的型号或硬件版本用的 | 看作者说明是否明确支持；只有文件名相似不够，没写清楚就先别刷 |
| 包没下载完整，或缺少文件 | 按作者提供的校验值检查下载文件；解压报错或缺文件就重新下载 |
| 把不同包里的系统和启动文件混在一起 | 使用同一套配套文件，不要自己东拼西凑；不匹配可能无法开机 |
| 新系统不支持你要保留的原基带 | 可能开机后没有信号或不能上网；先查作者的兼容说明，不确定就先停下 |
| 包需要额外补丁，但说明不清楚 | 看作者说明和刷机脚本是否有额外操作；不能猜着添加或省略，也不能仅凭包名判断 |
| 刷写位置、文件大小或启动设置不适合你的设备 | 先让 AI 对照本机分区和脚本检查；本仓库的刷写清单不能直接套到其他设备 |

换成 WinUSB 解决的是电脑和设备之间的通信问题，**不会让不合适的系统包变得兼容**。本次保留了原基带和联网设置，没有用包里的基带替换它们。

## 刷写、发现副作用并恢复

**公开版对应脚本：** [f50.py](../scripts/f50.py) 负责生成计划、保存刷前内容、检查、清用户数据和重启；[run_spd_plan.py](../scripts/run_spd_plan.py) 执行系统写入和读回；两者需配套 [f50lib.py](../scripts/f50lib.py)。下文的现场异常恢复没有做成通用自动脚本。

这次只刷了事先核对好的 14 项系统和启动文件，没有换掉原基带、联网配置和底层启动加载器。清理了系统临时数据，设置好从新系统启动，再把刷进去的内容读回来，与原文件对比，检查通过。

清用户数据时遇到一个坑：这个版本的 `e userdata` 不只清用户数据，还会清掉 `persist` 里的持久化设置，并留下恢复模式清数据的指令。发现后先没有重启，而是查清工具的实际行为，用**这台设备刷写前刚保存的备份**恢复被清掉的设置，再去掉多余的清数据指令，保留正常启动需要的设置。恢复后重新读取检查，确认与备份一致。

之后换成只清用户数据的方式，设备返回成功，并抽查了开头、中间和末尾，确认这些位置已清空。再检查需要保留的 21 项内容，结果都和刷写前一致，包括两套基带、联网配置、持久化设置和启动加载器。抽查不代表逐字节检查了全部用户数据。

检查完成后才发出重启命令，设备返回已接受。公开脚本已经避开上面那个清数据命令，并增加了保护检查；新增部分做过离线测试，还没有重新跑完整的设备实测。现场用到的恢复办法也没有做成给所有设备通用的一键操作。技术细节见 [命令说明](commands.md) 和 [验证范围](validation.md)。

## 启动后的结果

设备启动后确认进入目标 B09 系统，USB 网络和移动数据连接恢复。只记录这些功能结果，不公开设备后台返回的版本字符串、基带读数或个人设备标识。

ADB 仍未确认可用，TCP 5555 未开放；后台认证/调试请求未得到可验证的成功结果。本教程不声称 Root、ADB、禁止升级或任何额外应用已经安装成功。

## 可推广与不可推广的结论

WinUSB/LibUSB 在这个案例中绕过了 Windows U2S 串口写入路径，使完整备份和刷写得以进行。它不能解决错误固件、错误 FDL、机型不兼容或硬件损坏。保护数据的可靠依据是刷前快照与刷后读回比较，而不是包名里的“原版基带”字样。
