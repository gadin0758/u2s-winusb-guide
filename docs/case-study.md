# 实测记录：F50 B15 → B09，保留原基带和 NV

这是一个设备的结果，不是所有 F50 或所有中兴设备的兼容性保证。仅发布过程和统计，不公开原镜像、后台密码、设备身份和原始日志。

## 起点与通信问题

原系统 B15，用户不愿短接，ADB 未可用。SPRD U2S Diag 能显示 COM 口，原 signed sprdvcom 4.20.42.134 绑定正确，但通信发生串口写入错误（现场 Windows 写入超时 121）。关闭占用程序、改变线/接口后仍出现问题，不能简单归因于漏装驱动。

对 `1782:4D00` 下载设备改绑 WinUSB，使用 LibUSB 后端；分开 mode 2 请求与重新枚举交接，成功加载 FDL2。修改过的原驱动注册表设置已经恢复，教程不依赖那些改动。

## 先完成备份

读取 75 个 GPT 分区 + splloader，共 76 个镜像、31,269,847,040 字节，另存 32 KiB pgpt。GPT 两项 CRC、全部文件大小、流式 SHA-256 与磁盘 SHA-256 通过。userdata 使用 64 位物理读取，两套 NV 保留各自头部；未使用会跳过数据分区的 `r all` 作为完整备份。

完整备份保存在本地，开源版本不会包含其文件或个人路径。

## B15 Root 尝试与恢复

曾根据 B15 包写入 patched trustos/boot 并读回校验，但未取得可验证的 ADB Root。之后将原 B15 trustos/boot 恢复并读回校验，USB 网络和 5G 恢复。**不能把镜像写入成功当成 Root 成功，也不能把临时 USB 网络缺失当成永久变砖。**

## 选择配套 B09 系统

核对本地整套 B09 包：super/boot/vendor_boot/验证链配套，包中的活动 A 槽 nr_modem、nr_phy 与原设备 B15 A 槽镜像完全一致。B 槽包镜像与设备原 B 槽并不完全一致，因此两套原基带都保留，未刷入包里的基带。

保留了包作者最终覆盖的 trustos 镜像和整份 B09 super，没有仅提取 system 后与 B15 vendor 混搭。包里的 ztepersist 检查未发现明确的基带兼容补丁说明；查看到的是统计用途内容。也没有可靠作者变更日志或完整 pristine B09 对比，**无法证明包中存在或不存在所有隐含的 B15 专用优化**。本次兼容证据是配套镜像、相同活动基带/PHY以及启动后的实际网络结果。

## 刷写、发现副作用并恢复

系统使用固定 14 项白名单，仅 A 槽系统启动链和 super；SPL/UBoot、两套 modem/PHY、NV 均未刷入其他镜像。metadata/cache 清除，A 槽设置完成，14 项完整读回的源覆盖范围 SHA-256 匹配。

现场运行 `e userdata` 后发现固定版本工具实际写了 recovery wipe 命令并擦除 persist。这一步发生过，不能描述为 persist 从未被写动。停止重启，查源码后，从**紧邻刷写前的本机快照**恢复 persist 并比对哈希；只清除 misc 的前 2048 字节 recovery 命令，保留偏移 0x800 的槽位控制。恢复后读回匹配。

随后原生请求仅擦 userdata，ACK 成功，起点/中点/末端各 64 KiB 抽查为空白。21 项保护分区刷后与刷前快照一致，其中包括两套基带/PHY、NV、persist 和启动加载器。基带/NV 未被写入替代镜像。发布版额外保护 pm_sys_a/b，并在破坏性操作前再次读回保护内容；这属于新增检查，不是现场 21 项报告的扩展实测。

最后使用原生 reset，下载程序 ACK。发布脚本已规避 `e userdata` 封装，不把现场恢复 persist/misc 的操作自动推广到其他设备。

## 启动后的结果

设备启动后确认进入目标 B09 系统，USB 网络和移动数据连接恢复。只记录这些功能结果，不公开设备后台返回的版本字符串、基带读数或个人设备标识。

ADB 仍未确认可用，TCP 5555 未开放；后台认证/调试请求未得到可验证的成功结果。本教程不声称 Root、ADB、禁止升级或任何额外应用已经安装成功。

## 可推广与不可推广的结论

WinUSB/LibUSB 在这个案例中绕过了 Windows U2S 串口写入路径，使完整备份和刷写得以进行。它不能解决错误固件、错误 FDL、机型不兼容或硬件损坏。保护数据的可靠依据是刷前快照与刷后读回比较，而不是包名里的“原版基带”字样。
